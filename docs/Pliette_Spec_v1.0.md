# Pliette（纸栖）开发 Spec

版本：1.0 · 更新日期：2026-09-07 · 建议仓库名：`pliette`

定位：由 Spine 纸片角色、参数化动作和有限 3D 场景构成的桌面 AI 伴侣。

文档状态：可用于启动新仓库的实施规格。真实拉菲 `lafei_8.zip` 已核查部分结构：导出版本为 Spine 3.6.52，含 79 根骨骼、42 个 Slot 和两条腿部 IK。依用户最新决定，另一会话的自制渲染实验不作为本项目依据或依赖。技术选择为项目决策，性能数字为验收目标；本文示例参数尚未在官方运行时中的目标角色上验证。

阅读导航：第 3–6 节确定技术与创作路线；第 7–9 节是参数、并行和混合的核心设计；第 14–15 节规定实施与验收；附录 B 用于启动开发 Agent；附录 D 记录真实拉菲资产信息及官方运行时接入要求。

## 1. 项目决策与边界

### 1.1 名称

新项目名定为 **Pliette**，中文名 **纸栖**。名称呼应轻巧的折叠、纸片与陪伴感，作为独立项目代号使用，不暗示特定模型或游戏引擎。仓库、包名前缀和应用标识统一使用 `pliette`；角色本身可另起名字。

### 1.2 核心目标

Pliette 使用现有的 Q 版 Spine 角色资源，保留正反面和纸片特征。先验证 **LLM 能否为真实骨架生成协调、自然、可复用的数值动作参数**，再逐步建立动作库、并行动作调度和桌面交互。

第一阶段的成功标准是得到可反复播放、可混合、可中断的动作录像，以及可追溯的参数文件。对话、桌面常驻、精致房间和大量动作都排在这项验证之后。

长期主体采用：**Spine 原生动画能力 + 角色专用骨骼绑定 + 参数化动作预置 + 属性级组合调度 + 场景接触约束**。运行时 LLM 选择动作并填写受限参数；它也可以在实验室中生成新的关键帧参数，经过检查后进入动作库。

### 1.3 已确定的范围

| 项目 | 本项目决定 |
| --- | --- |
| 角色 | 首个对象为已提供的拉菲 lafei_8，Spine 3.6.52；正反面的具体组织形式仍需完整播放核查 |
| 动作数据 | 直接处理原生 2D 骨骼、Slot、Attachment 和动画；不做成人 3D 动作到 Q 版的投影或重定向 |
| 动作生成 | 优先测试 LLM 输出稀疏关键帧及动作参数；初期运行使用审阅后的预置 |
| 动作播放 | 使用与资源版本匹配的 Spine 官方运行时，复用插值、混合和约束能力 |
| 场景 | 有限的真实 3D 房间，角色作为具有正反面的纸片演员存在 |
| 并行动作 | 由身体部位、实际属性所有权、姿态和接触条件共同决定 |
| 工程组织 | 新建独立小型项目；自研业务逻辑，使用必要的底层图形与骨骼库 |
| 旧 Rayure | 保留为已有工作的参考；本 Spec 不要求删除、关闭或迁移旧仓库 |

### 1.4 当前不建设

不接入 ARDY、CMU、HumanML3D，不建设通用重定向系统、海量风格提炼管线、自动建骨骼系统或任意人体动作生成服务。不从零重写 Spine 播放器，不搭建多引擎兼容平台，不在第一阶段实现多角色互动、任意家具物理交互或 Windows 壁纸嵌入。

这些边界用于集中验证成本；未来扩展必须由具体需求和实验结果推动。

## 2. 动作质量假设与验证策略

### 2.1 要验证的假设

LLM 在获得真实骨骼结构、角色图像、旋转方向、动作范例及合法参数范围之后，可以用较少的迭代生成可接受的 Q 版动作。这里的“可接受”包含身体协调、节奏、轮廓和角色风格，不能只检查 JSON 能否解析。

该假设需要在正确显示原角色的官方运行时上验证。自制渲染造成的外形失真，会混淆资产接入问题与参数质量，不能用来评价这条动作路线。实际拉菲有 79 根骨骼，其中大量节点服务于头发、衣服和装饰；对 LLM 开放少量语义控制器即可，无需删减原骨架。

### 2.2 三种 LLM 工作模式

| 模式 | 输入与输出 | 使用阶段 |
| --- | --- | --- |
| Tune：参数生成 | 输入固定 Primitive、真实骨骼绑定和参数域；输出幅度、节奏、阶段等数值参数 | 首要实验；明确区分参数变化与函数改写 |
| Author：曲线创作 | 输入角色检查报告、骨骼绑定、图片和动作要求；输出含数值关键帧的 `MotionDraft` | 固定 Primitive 表达不足时进行受控对照，允许新建动作 |
| Select：行为选择 | 输入场景、当前姿态、手部占用和对话；输出简短 `MotionIntent` | 预置动作可用后接入运行时 |

不能把“从菜单选择一个已有动作”算作 LLM 创作动作验证。也不能把人工重新制作后的结果计入 LLM 一次生成的质量。

### 2.3 对照实验

选取一名角色和六项低风险动作：轻微待机、点头、单手小幅挥手、指向、倾身倾听、害羞收缩姿态。缺少所需部位时，记录缺失并替换为该角色确实支持的动作。

每项保留三种结果：原资源中的相关动作或静态参考；LLM 首次生成且未修改的结果；最多三轮可视反馈后的结果。反馈可以来自开发 Agent 的截图与视频检查，也可以来自用户。任何人工改动必须单独标记，保留原始候选。

所有结果使用相同角色、镜头、速度和录制条件。先判断局部动作是否成立，再测试混合与并发，最后放进房间。实验阶段不得用精致场景、镜头切换或后期处理掩盖动作问题。

### 2.4 原角色保真是前置条件

用户已明确放弃参考另一会话的自制 Spine 渲染实验。本项目不继承其播放器、动作质量结论或通过率，也不以等待该实验产物作为启动条件。独立核查的原始资产版本、骨骼和约束信息保留，详见附录 D。

第一个可运行产物必须是“官方运行时正确播放原动画”的 Lab。关闭全部新参数时，角色应恢复原资源的形状、部件、透明度、层级与动画。原动画已经失真时，停止动作质量评分，先修复导入和渲染接入。

参数层只生成受限数值、Timeline 和编排命令；网格蒙皮、Deform、绘制顺序、裁剪、贴图坐标与骨骼约束由官方实现承担。随后固定 Primitive 与 RigProfile，让 LLM 只生成参数；必要时对照稀疏关键帧创作，再加入多部位并行、局部取消和接触。

## 3. 技术栈与架构

### 3.1 单一实现路线

| 层 | 选择 | 原因与限制 |
| --- | --- | --- |
| 语言与构建 | TypeScript、Vite、npm 锁文件 | 前端、参数验证和场景共享类型；降低工程起步成本 |
| 3D 场景 | Three.js，先用 WebGLRenderer | 足够承载小房间、相机和纸片演员；初期不引入物理引擎 |
| Spine | 首个角色锁定官方 `spine-ts` 3.6 core / webgl；旧二进制导入单列 | 保留原生 Mesh、Deform、Slot 和约束；不能假设 3.6 Web Runtime 自带 skel 读取器 |
| Spine 接入场景 | 透明 HTMLCanvasElement → Three.js CanvasTexture → 正反面平面 | 隔离 Spine 版本与 Three.js 适配器耦合；有纹理更新成本，必须测量 |
| 实验室界面 | 原生 DOM/CSS，必要的小型控件 | 先满足导入、调参、对照、日志和录制，不引入复杂 UI 体系 |
| 参数验证 | JSON Schema + Ajv 或同等严格校验 | 结构约束与业务约束分开；禁止执行 LLM 输出的脚本 |
| 自动验证 | Vitest 验证关键规则；Playwright 驱动浏览器；FFmpeg 整理录像 | 测试组合与中断风险；不堆叠镜像实现的测试 |
| 桌面宿主 | 浏览器实验通过后使用 Electron | 复用同一渲染器；Windows 为首个目标平台 |
| LLM / TTS | 通过窄接口适配已有服务 | 初期允许文件导入与假事件，不以外部模型部署阻塞动作验证 |

Spine 的导出数据和运行时需要匹配 major.minor 版本。当前拉菲已确认是 3.6.52，首个适配器使用 3.6 数据语义，准确依赖提交和本地构建哈希写入锁定记录与 `docs/asset-report.md`；不直接安装最新 4.x 加载该资源。[Spine 版本策略](https://esotericsoftware.com/spine-versioning)

必须另行解决旧二进制导入：官方 spine-ts 的二进制加载支持在 3.8 才加入，3.6 Web 运行时不能仅凭“版本匹配”便直接读取该 skel。首版采用一次性导出同版本 JSON，再由官方 3.6 SkeletonJson 加载；优先使用兼容版本的 Spine 编辑器导入和导出，保留原图集、全部网格、权重、约束和动画。该步骤是文件表示转换，不是 3D→2D 或骨架重定向。[Spine 3.8 发布说明](https://en.esotericsoftware.com/blog/Spine-3-8-released)、[Spine 数据导入](https://en.esotericsoftware.com/spine-import)

若开发环境没有可用转换工具，P0 应明确报告“3.6 二进制导入尚未解决”，继续完成可独立推进的接口、Schema 与官方样例验证。需要自动化时，另立一个基于官方 3.6 二进制读取实现的离线转换工具任务；它只负责文件解码与表示转换，并以原动画采样对照验收，不实现新的姿态求解或渲染。不能因导入受阻而用自制简化播放器冒充完成接入。

“自研”指动作语义、参数管理、编排和产品逻辑由项目掌握。采用 Spine 和 Three.js 不意味着依赖另一个桌面伴侣项目的架构。

### 3.2 模块责任

| 模块 | 负责 | 输出 |
| --- | --- | --- |
| Asset Inspector | 读取资源版本、骨骼、约束、动画与正反面组织 | `AssetReport`、可视探针 |
| Rig Adapter | 将语义部位绑定到真实骨骼，转换单位和方向 | `RigProfile`、`CapabilitySet` |
| Motion Authoring | 准备 LLM 上下文、保存候选、预览和比较 | `MotionDraft` |
| Motion Compiler | 验证候选，解析参数，生成匹配版本的 Spine Timeline | 可播放动画与属性清单 |
| Parameter Registry | 分类、继承、限制参数，管理版本和预置 | 解析后的不可变参数快照 |
| Motion Scheduler | 处理并行、序列、抢占、占用、取消和姿态转换 | 每条动作通道的执行计划 |
| Pose Composer | 应用原生轨道、允许的偏移及最终约束 | 当前完整 Spine 姿态 |
| Scene Controller | 世界移动、角色朝向、物件和交互锚点 | 世界变换与接触目标 |
| Speech Adapter | 对齐实际播放时钟，输出嘴型和说话状态 | 可取消的语音事件 |
| Host | 桌面窗口、存储、受限系统接口 | 平台服务 |

### 3.3 数据链路

创作链路：`真实资产 → 检查与绑定 → LLM MotionDraft → 校验与预览 → MotionPreset`。

运行链路：`对话或输入事件 → MotionIntent → 参数解析与调度 → 动画混合 → 接触修正 → Spine 渲染 → 3D 场景`。

场景上下文参与调度前的可行性判断，并为最后的接触修正提供目标。语音、视线和自主待机可以独立提交意图，但不能绕过属性所有权。

## 4. 资产导入、正反面与骨骼

### 4.1 第一件事：确认能正确播放原动作

导入 `.skel` 或 `.json`、`.atlas` 及全部纹理页，生成检查报告。接受本次资源实际使用的 `.atlas.txt`，按内容识别为 atlas，无需修改原文件。报告必须列出导出版本、atlas 页、骨骼层级、Slot、Attachment 类型、Skin、约束、动画名称与时长、事件，以及正反面组织方式。先按第 3 节准备匹配的加载链；若无法解析，明确失败文件与版本，不尝试把二进制当文本修补。

基线播放器应正确显示原有 Mesh、变形、透明混合、裁剪和绘制顺序。缺失贴图、黑边、错误缩放等属于资产接入失败，不应通过调整 LLM 动作参数掩盖。

没有实际用户资产时，可以使用官方示例验证播放器管线，但必须把“管线可用”与“用户角色可用”分开报告。

### 4.2 正反面的三种可能结构

| 实际结构 | 处理方式 |
| --- | --- |
| 同一骨架的不同 Skin / Attachment | 创建前后视图实例，使用明确的 Skin / Attachment 配置 |
| 同一文件内通过特定动画、Slot 或绘制顺序切换 | 在角色清单中声明切换机制；不假设改 Skin 就能生效 |
| 两套独立骨架与贴图 | 分别加载和绑定，统一逻辑动作、阶段和事件；不能假设骨骼名称一一对应 |

用户描述的正反面是当前资产需求，不是所有 Spine 文件的默认特性。本次 lafei_8 包只有一组 skel、图集和纹理；这既不证明只有正面，也不证明存在完整背面。须在完整加载后确认视图机制。参数实验可先用已验证视图继续；背面未核实前限制展示朝向，不把镜像正面当作背面，也不以背面资料缺失阻塞全部 P1 工作。

### 4.3 RigProfile：角色专用的语义绑定

RigProfile 保存真实骨骼名称、父子关系、局部坐标方向、旋转正负、参考姿态、可用范围与能力。它不是第二套骨架，不重命名或重建原文件节点。

首个角色可以由 Agent 辅助完成有限绑定：读取层级、观察截图，再对候选骨骼施加小幅正负旋转探针，例如 ±5°，确认控制对象与方向。自动名称匹配只产生候选，不能跳过可视确认。

| 语义部位 | 可能对应 | 注意事项 |
| --- | --- | --- |
| body.root / body.hips | 躯干、腰或根部节点 | 世界移动由场景控制；动画只负责局部起伏 |
| body.chest | 胸部或躯干上段 | 可能不存在；禁止把整张身体贴片当作独立腰胸结构 |
| head.main | 头部父节点 | 受大头轮廓、发饰和面部子节点影响 |
| arm.left / arm.right | 上臂、前臂、手或整臂节点 | 缺少肘部时只开放整臂动作，不伪造弯肘能力 |
| leg.left / leg.right | 大腿、小腿、足或整腿节点 | 只有一段腿时不能声称拥有双骨 IK |
| face.eyes / face.brows / face.mouth | Slot、Attachment 或可动骨骼 | 具体能力由资产决定；Spine 不自动提供 3D BlendShape |
| secondary.hair / accessories | 头发、衣服和饰品 | 优先复用资源原有动画，避免重复驱动 |

### 4.4 坐标与单位

世界为右手坐标，Y 向上，地面为 XZ。角色标定身高为 H，默认 H = 1 世界单位。记录固定的 Spine 参考身高 `skeletonHeightUnits`，作者格式中的二维位移使用 H 的比例，编译时换算为 Spine 原生单位。

旋转使用角度，默认相对绑定参考姿态；缩放使用倍率，1 为原始尺寸。左右一律指角色自己的左右。RigProfile 为每个视图保存方向换算，不通过相机左右猜测。

角色世界平移与整体转身属于 `actorRoot`。骨骼根部的小幅 bob、倾身和压缩属于局部动作。一个动作不能同时通过骨骼根移动和场景位移重复推进角色。

### 4.5 能力清单

每个角色声明可以执行的动作族与支持视图，例如 `wave.right`、`point.left`、`look.eyes`、`sit`、`mouth.attachments`。能力由绑定、图像覆盖和已验证动作共同决定。只有站立素材不等于可以自然完成趴、躺、爬；不足时需要专用姿态、Attachment 或新美术。

同一逻辑动作若只有正面实现，演员背向相机时不得假装背面也可播放。调度器应按动作策略先转向、选择已批准替代动作，或返回能力不足。

## 5. 渲染与场景选择

### 5.1 采用完整 Spine 画面作为纸片表面

Spine 官方 WebGL 渲染器先把完整角色绘制到透明 HTMLCanvasElement，再把画布作为 Three.js CanvasTexture。角色内部仍然是原生骨架、Mesh 和 Slot，场景中的纸片只是渲染结果的承载面。[Spine Runtimes](https://en.esotericsoftware.com/spine-runtimes)、[Three.js CanvasTexture](https://threejs.org/docs/pages/CanvasTexture.html)

首版使用两个方向相反的平面，分别承载正面和背面，法线为局部 +Z 和 −Z；材质仅渲染各自正面，避免同时叠加和错误镜像。两面可以共面；若驱动或透明排序出现问题，使用极小、固定的间距。角色整体可以在世界中旋转，侧面变薄是允许的视觉风格。

演员初始使用 MeshBasicMaterial，启用透明与深度测试，关闭深度写入；场景先限制为不透明家具和一个角色，避免同时引入多层半透明排序问题。角色内部层级始终由 Spine 管理，外部场景只管理完整演员的遮挡关系。

这一步把二维原生角色放进三维场景，没有引入 3D 人体动作到 2D 骨骼的转换。

### 5.2 纹理、透明与性能约束

首版单个视图的画布边长上限暂设 1024 像素，实际尺寸根据原图和屏幕显示面积选择。使用跨动作稳定的画布范围和脚底基准点；不得每帧自动适配包围盒，否则角色会产生缩放与位置抖动。

每帧先完成 Spine 绘制，再标记 CanvasTexture 更新并渲染场景。不创建新纹理、不使用 `toDataURL`、不做逐帧 CPU `readPixels`。画布跨 WebGL 上下文的更新仍可能产生拷贝或上传成本，不能把它描述为免费共享显存。

透明度、预乘 alpha、颜色空间、绘制缓冲区生命周期和纹理过滤必须通过黑、白、彩色背景验收。优先在同一渲染循环完成绘制与纹理使用；如需开启 `preserveDrawingBuffer` 才能满足目标环境，应记录成本并测量。不要靠重复透明混合掩盖黑边。

前后视图共享动作时间；隐藏视图可以跳过实际绘制，但重新可见时必须同步到当前姿态，不从零开始动作。首次实现可同时更新两个视图，性能优化以测量结果为依据。

### 5.3 整张纸片的交互上限

3D 深度缓冲只看见演员平面，无法自动把一个 3D 杯子插入平面内部的“手与身体之间”。首版抓取使用靠近角色平面的握持点，明确物件在角色前方或后方。触碰桌面、站到指定点和坐到已知位置可以通过锚点完成。

需要物件穿插手臂与躯干、复杂遮挡或立体包围式拥抱时，必须增加分层渲染或专用遮罩。该需求触发独立架构评审，不能用更多动作参数解决。

官方 spine-threejs 直接 Mesh 集成可作为后续优化候选，但首版不同时维护两套渲染后端。只有纹理路径出现明确的性能或深度交互瓶颈，并确认资产版本兼容后，才重新选择。[Spine Three.js runtime update](https://esotericsoftware.com/blog/spine-threejs-runtime-update)

### 5.4 两个场景模式

**Motion Lab** 是首个开发入口：中性背景、地面参考线、固定镜头、原动作列表、骨骼高亮、参数编辑、暂停逐帧、时间线、事件日志和录像按钮。正反面对照与参数原文必须容易访问。

**Room** 在动作验证后实现：一个小房间，包含地板、墙、桌椅、坐垫与一个可持物件，先由 Three.js 基础几何体构成。角色保持贴图原有色彩，配合简单接触阴影；无需一开始建设 PBR 人物或动态全局光照。

产品主镜头建议透视视场角约 35°，位置约 `(0, 1.5H, 4.5H)`，观察 `(0, 0.8H, 0)`，允许有限视差，例如水平 ±12°、俯仰 ±6°。这些是初始构图值，需要按真实角色调整。调试模式保留自由轨道相机以检查侧面和背面。

角色在已知地面范围内移动，使用少量路点和静态障碍边界，不能直线穿过桌椅。初期没有必要引入完整导航网格或刚体系统。

## 6. 动作创作与“补间生成器”的分工

### 6.1 四种不同能力

| 能力 | 实现者 | 能做到什么 | 不能自动做到什么 |
| --- | --- | --- | --- |
| 关键帧插值 | Spine Timeline | 在已有帧之间计算曲线 | 设计一个漂亮的挥手 |
| 动画混合 | Spine AnimationState | 淡入淡出、轨道叠加、队列与中断 | 保证任意站躺过渡合理或脚不滑 |
| 参数化模板生成 | 本地动作函数；可参考 spine_anim_mcp | 根据 stride、bob 等生成已设计模式的曲线 | 从名字推导任意新动作的运动规律 |
| 动作参数创作 | LLM + 预览反馈 | 为特定骨架提出关键帧、节奏和幅度 | 保证首次结果达到动画师质量 |

Spine 官方运行时负责前两项。`spine_anim_mcp` 是第三项的参考：目前公开说明包含 idle、walk、run、jump、attack、hit 等生成器，但它不是一个已经解决所有角色动作与接触的成熟系统。先阅读、选择性借鉴，不把它或 MCP 服务设为运行时必需依赖。[Applying animations](https://esotericsoftware.com/spine-applying-animations)、[spine_anim_mcp](https://github.com/K-ulucay/spine_anim_mcp)

如果后续确认用户所指的“补间参数生成器”是另一个具体项目，应对照此表判断它替代哪一层；在没有项目地址和 API 前，不预设其能力。

### 6.2 MotionDraft 创作流程

输入包包含：资源检查报告、相关正反面截图、RigProfile、可用动作参考、允许属性、数值范围、动作目的、时长范围和输出 Schema。只提供名称列表而不给局部轴方向，容易生成反向抬臂或穿身动作。

LLM 输出严格 JSON，采用语义部位与数值曲线。Compiler 负责绑定到真实骨骼，并构造版本匹配的官方 Animation / Timeline 对象。无需为了添加动作而强制把原始 `.skel` 全量转成另一种格式。

内部 MotionDraft 的字段与归一化 Bézier 是项目协议，不能不经转换直接当作某个版本的 Spine 导出 JSON。Compiler 必须通过实际运行时的采样结果验证转换。当前 3.6 旋转 JSON 使用 angle；内部 value 应显式映射，或直接构造官方 Timeline。版本差异由适配器处理，不交给 LLM 猜测。

候选先经过结构、时间、属性、幅度和能力校验，再预览。失败应生成明确诊断，保留原始候选；允许 LLM 根据诊断修订。禁止把候选内容作为 JavaScript、Python 或着色器执行。

### 6.3 初始创作限制

第一轮每项动作建议 0.6–3 秒、3–6 个相关控制部位、每条曲线 3–8 个关键点。它们是减少搜索空间的默认值，不是对所有动作的硬性上限。循环待机和行走可使用不同预算。

曲线仅开放 `linear`、`stepped` 和有界三次 Bézier。Bézier 时间控制点限定在 [0, 1] 且时间单调；第一阶段将值控制点也限定在 [0, 1]，过冲用显式关键点表示，便于观察和限制。

所有导出的动作声明准备、主要表达、保持或循环、恢复阶段。挥手重复仅重复主要挥动段，不为每一轮重新抬手和落手。

### 6.4 MotionDraft 示例

以下仅展示数据契约，数值不代表已验证的动作。`role` 通过当前视图的 RigProfile 绑定，旋转值由参考姿态和方向映射换算。

```json
{
  "schemaVersion": 1,
  "id": "wave_small_right_candidate_01",
  "rigProfile": "first-character.front.v1",
  "durationSec": 1.6,
  "channels": ["rightArm"],
  "phases": {
    "prepareEnd": 0.3,
    "strokeEnd": 1.2,
    "recoverEnd": 1.6
  },
  "curves": [
    {
      "role": "arm.right",
      "property": "rotate",
      "mode": "relativeToReference",
      "keys": [
        {"t": 0.0, "value": 0, "ease": "linear"},
        {"t": 0.3, "value": 22, "ease": "linear"},
        {"t": 0.6, "value": 14, "ease": "linear"},
        {"t": 0.9, "value": 26, "ease": "linear"},
        {"t": 1.2, "value": 18, "ease": "linear"},
        {"t": 1.6, "value": 0, "ease": "linear"}
      ]
    }
  ],
  "requirements": {"postures": ["standing", "seated"]},
  "provenance": {"kind": "llm", "candidate": 1},
  "approval": "draft"

```

这里用整臂语义说明格式。真实角色若有上臂、前臂、手腕，可以扩展角色绑定和曲线；若没有，就必须通过现有部位的配合提升效果。

### 6.5 从 Draft 到 Preset

MotionPreset 是通过审阅、固定版本的可复用动作，包含源 Draft、允许调节的参数、合法姿态、视图支持、属性写集、接触要求、阶段、混合策略和来源记录。动作库可以直接包含优质原资源片段，并注明来源；不能把它们计入 LLM 新生成动作的成功率。

保存原始 LLM 输出、提示词、可获取的模型标识、骨架版本、截图、修订历史和动作哈希。开发 Agent 自身可以承担第一轮 Author 工作；如果尚未提供模型服务，使用文件导入即可，不虚构已经调用某个 API 或测得模型延迟。

## 7. 参数集模块：分类、继承与组合

### 7.1 设计原则

参数模块需要同时回答：这个值的单位是什么，谁能修改它，影响哪个部位，与哪些动作兼容，什么时候生效，以及发生冲突时由谁决定。

不能把所有数字放进一个松散字典，也不能用一个全局 `intensity` 同时放大头、手、脚和位移。相同情绪在不同动作上需要不同映射；持续持物与短暂挥手也不能用同一种权重规则处理。

### 7.2 七类数据

| 类别 | 内容示例 | 修改者与生命周期 |
| --- | --- | --- |
| RigProfile | 骨骼绑定、参考姿态、符号、关节范围、身高标定 | 导入与校准流程；运行中只读 |
| ActionParams | amplitude、tempo、cycles、手侧、目标 | 动作特有；允许用户或 LLM 在已批准域内赋值 |
| StyleProfile | 某动作族的头倾、身体弹性、节奏偏好 | 角色与动作族的稀疏配置；版本化 |
| TransitionPolicy | 混合时长、退出阶段、可中断点、恢复方式 | 动作作者或系统配置；LLM 默认不能任意覆盖 |
| MotionRecipe | 顺序、并行、触发标记、依赖、失败处理 | 行为编排；引用动作与参数，不能写裸骨骼 |
| RuntimeContext | 当前姿态、手部占用、接触、朝向、物件位置 | 实时系统事实；LLM 无权改写 |
| MotionPreset | 已批准的动作曲线及以上配置的引用 | 动作库；不可原地修改已在播放的版本 |

### 7.3 参数声明必须包含的字段

每个可调参数声明 `type`、`unit`、`default`、有效域、适用动作、影响通道、映射方式和生效时机。数值参数还要区分硬限制与已验证范围。

| 参数例子 | 单位与作用 | 合法使用方式 |
| --- | --- | --- |
| amplitude | 无量纲；对动作参考中心的偏移幅度 | 仅缩放批准的表达曲线；不缩放绝对位置或握持目标 |
| tempo | 1 为原速；作用于逻辑阶段时长 | 受动作范围限制；不独立改变世界行走速度 |
| cycles | 整数；主要循环次数 | 只重复 loop / stroke 区间 |
| strideH | H；步幅 | 只属于步态；与世界速度和步频联合求解 |
| bodyBobH | H；身体上下起伏 | 对支撑脚有影响，最终必须经过接触检查 |
| hand | left / right / auto | auto 才允许调度器换手；按角色解剖方向解释 |
| target | 有类型的场景对象或锚点引用 | 运行时解析，不允许任意访问路径 |
| headTiltDeg | 度；头部表达偏移 | 与视线、点头共同交给头部控制器预算 |
| mixInSec | 秒；进入混合 | 默认属于 TransitionPolicy，不作为情绪强度的附带乘数 |

不把所有参数开放给所有动作。`sit` 不接受 stride，`look_at` 不接受挥手 cycles；无效字段应返回可读错误。

### 7.4 参数解析顺序

按以下顺序构造一次动作的参数快照：动作定义默认值 → 角色专用默认值 → 命名预置 → 请求中明确允许的覆盖值。随后应用已声明的 StyleProfile 映射，再执行能力、姿态、属性与数值校验。

StyleProfile 的每个映射说明是“补默认值”“有界倍率”还是“偏移”，不能使用隐含的多轮乘法。显式设置了绝对目标、接触位置或绝对关节角时，不再被风格倍率改写。

范围外的作者数据应拒绝并报告。运行中的数值稳定保护可以临时限制异常值，但必须记录诊断，不能把被大幅裁剪的动作当作原意图成功执行。

### 7.5 风格是动作族的配置

第一版只做少量有辨识度的配置，例如 neutral、happy、shy、tired。每个配置仅影响允许的动作族。`happy + wave` 可以增加抬臂幅度和主要段速度；`happy + hold_cup` 不应晃动握持点。

`emotion` 用于选择预置或映射规则，`intensity` 决定该映射在批准范围内的程度。无法证明连续插值合理的两个姿态，不进行盲目数值插值。害羞与生气的不同轮廓可以拥有少量专用曲线，不强求一个模板覆盖所有语义。

### 7.6 参数集示例

以下为预置配置示意。参数域是待实测的起始范围；进入正式库前必须记录实际验证范围。

```json
{
  "id": "wave.small.happy.v1",
  "action": "wave",
  "implementations": {
    "right": {
      "curvePreset": "wave_small_right_approved_v1",
      "requiredChannels": ["rightArm"]
    },
    "left": {
      "curvePreset": "wave_small_left_approved_v1",
      "requiredChannels": ["leftArm"]
    }
  },
  "defaults": {
    "hand": "right",
    "amplitude": 0.75,
    "tempo": 1.0,
    "cycles": 2
  },
  "overrides": {
    "hand": {"enum": ["left", "right", "auto"]},
    "amplitude": {"min": 0.6, "max": 1.0},
    "tempo": {"min": 0.85, "max": 1.2},
    "cycles": {"min": 1, "max": 3, "integer": true}
  },
  "style": "happy.gesture.v1",
  "transition": "gesture.soft.v1",
  "optionalChannels": ["torso", "head"]
}
```

`requiredChannels` 定义动作成立所必需的资源；`optionalChannels` 定义可降级的装饰动作。走路时可以保留右臂挥手，降低身体弹跳；如果右臂被占用，不能只播放头倾后声称完成了挥手。

`hand:auto` 在已实现且空闲的手侧中选择，再解析对应 implementation 的曲线和资源需求。左右变体必须分别验证；角色左右不对称时，不能仅把角度取负就认定自动镜像成立。视图变体由对应 curvePreset 的 viewImplementations 继续解析。

### 7.7 修改正在播放的参数

每项参数声明 `updatePolicy`：`nextAction`、`phaseBoundary` 或 `smoothLive`。手侧、动作族和姿态通常下次动作生效；循环次数可在循环边界调整；小幅 amplitude 可由短时平滑过渡更新。

实时更新不得直接重置 Timeline 的起点。tempo 改变应保持当前相位连续，重新计算后续时间；不能通过改变累计时间倍数导致瞬间跳帧。批准预置被编辑时生成新版本，已播放实例仍持有旧快照。

### 7.8 参数有效性与单位迁移

每个正式参数除 Schema 校验外，还要提供至少一个“影响证据”：固定姿态、阶段和随机种子，在有效范围内改变该参数，检查预期骨骼属性、锚点或可视轮廓确实变化。参数在准备阶段本来不生效时，应选择其声明的有效阶段测试。不能把“字段被接受”或“中间字典数值改变”当作最终驱动成立。

将 `affectedProperties`、`observableRoles`、`activePhases` 和有效性检查记录加入 ParameterDefinition。若参数只在某种能力或视图下有效，明确声明条件；失效参数应从该角色可选菜单与 LLM 能力表移除。

外部示例中的同名参数不一定具有同样单位。腿部摆角使用度，步幅使用 strideH，世界速度使用 H/s，振荡频率使用 Hz，重复次数使用整数 cycles。导入配置必须显式换算，保留原值和单位；不把浮点频率截断后当作重复次数。

### 7.9 控制器类型与真实骨骼的关系

ParameterDefinition 还应指向一个已绑定的 ControllerDefinition。控制器声明控制空间、实际属性写集、求解依赖与可观察部位；相同的“腿”在不同 RigProfile 下可以使用不同控制机制。

| 控制器类型 | 参数控制对象 | 拉菲首版的应用 |
| --- | --- | --- |
| localFk | 骨骼局部旋转、位移或缩放 | 手臂与头部表达；使用参考姿态偏移 |
| ikTarget | 现有 IK 目标点和经许可的 mix | leg_L / leg_R 的目标平移；原 IK 负责腿部求解 |
| slotState | 离散 Attachment 或 Slot 状态 | 眼睛与表情；必须依据实际附件清单 |
| actorWorld | 演员整体位置与朝向 | 场景控制器唯一持有，动作只提交目标 |
| composite | 协调多个已绑定控制器 | 害羞、跳跃等动作族；显式声明必需与可选部分 |

当前拉菲的 `leg_L`、`leg_R` 是腿部 IK 目标骨，链条分别为 `leg_L1 → leg_L3` 和 `leg_R1 → leg_R3`。初始步态优先输出目标轨迹，由原有 IK 求解。IK 生效时，不能同时把链上旋转当作另一套独立控制参数；如果需要 FK 动作，必须连同 IK mix 一起切换并验证过渡。

腿部控制器拥有目标平移、必要的 IK mix 与支撑阶段信息；两骨 IK 的存在并不等于世界锁脚已经实现。世界接触仍需转换坐标、处理演员移动并测量误差。对 `ik:leg_L/mix` 等求解器属性同样实行所有权，不允许装饰动作随意关闭约束。

## 8. 多部位并行动作与冲突处理

### 8.1 身体分区只是入口，属性所有权才是依据

提供 `base`、`leftArm`、`rightArm`、`torso`、`head`、`face`、`mouth` 等语义通道，但编译后必须得到真实属性写集，例如 `bone:arm_r/rotate`、`bone:body/translate`、`slot:mouth/attachment`。

对兼容旧版 Spine 的首版，translate 和 scale 的 X/Y 作为同一属性组处理。不能让两个轨道分别“只写 X”和“只写 Y”，却实际各自覆盖整个 TranslateTimeline。旋转也是一个真实局部属性，不能把不存在的三维 yaw、pitch 拆成两个独立控制权。

所有权包含父级依赖：一个持物动作可能只直接写手臂，但也依赖肩、躯干和角色根部的位置。调度器需要维护 `writes`、`dependsOn` 和 `contacts`，不能只检查骨骼名称集合是否相交。

### 8.2 固定轨道与轻量遮罩

| 轨道 | 主要职责 | 默认方式 |
| --- | --- | --- |
| 0：base | 站立、坐姿、步态、全身姿态转换 | 覆盖式基础姿态 |
| 1：leftArm | 左臂手势或持物姿态 | 限定属性覆盖 |
| 2：rightArm | 右臂手势或持物姿态 | 限定属性覆盖 |
| 3：torso | 小幅倾身、表达姿态 | 已批准覆盖或局部偏移 |
| 4：head | 视线、点头与头部表达的合成输出 | 单一头部控制器 |
| 5：face | 眼睛、眉毛等非嘴部表情 | 附件选择或已绑定属性 |
| 6：mouth | 嘴型、说话状态 | 语音控制器拥有嘴部属性 |

Spine AnimationState 支持多个轨道；高轨道只应写它拥有的属性。它不自动根据“上半身”这个名字生成遮罩。Compiler 必须过滤 Timeline，并对过滤后的写集进行审计。[Applying animations](https://esotericsoftware.com/spine-applying-animations)

导出的原动画可能给许多骨骼写了参考姿态，即便视觉上只在挥手。未经过滤直接放上高轨道，会覆盖双腿或躯干。过滤时还需检查 IK mix、约束和 Attachment 等间接影响；不可只删除旋转曲线就认为隔离完成。

上述轨道编号是执行布局，不是业务优先级。调度器先仲裁，再向固定轨道写入结果；不能靠不断增加轨道编号实现抢占。

### 8.3 合成方式

| 方式 | 使用场景 | 规则 |
| --- | --- | --- |
| Override | 手臂从自然摆动进入挥手 | 对拥有的属性淡入，结束后淡回基础层 |
| Additive | 小幅呼吸、头倾或身体微动 | 基于参考姿态的偏移；设总幅度预算；不得累计漂移 |
| Discrete | 嘴型、手型、表情 Attachment | 单一所有者；明确切换时刻与恢复对象 |
| Constraint | 支撑脚、持物点、场景触碰 | 在表达动作之后处理，优先满足已承诺的接触 |

只有确认当前 Spine 版本的混合语义适用后，才使用其 additive 能力；否则通过一个受控的局部偏移阶段实现小幅加法。偏移必须每帧从当前合成基准计算一次，不能对上帧结果不断累加。

禁止每帧无条件 `setToSetupPose()` 再播放，导致混合对象丢失或属性弹回。基础层应持续提供稳定姿态；采用匹配版本文档中的标准 AnimationState 更新和应用流程。

### 8.4 接触与资源占用

持物是持续状态，不能在 `pick_up` 动画结束后自动释放。抓取事件建立手部资源占用与物件绑定，放下事件才释放。事件由逻辑调度器发出一次，前后两个视图不得重复创建物件、播放音效或触发抓取。

第一版携带物件可以让物件跟随最终手部锚点。触碰固定桌面、脚底锁定等需要反向约束骨架的动作，使用资产已有的 IK 或明确的受限修正；没有足够关节自由度时返回不可达或调整演员站位。

先完成动作混合与风格偏移，再应用接触修正。不能先锁住脚，随后叠加 body bob 又把脚带离地面。使用现有 Spine 约束时，严格遵守该版本骨骼变换和约束更新顺序；不借用新版本专有 API。[Runtime skeletons](https://esotericsoftware.com/spine-runtime-skeletons)

### 8.5 组合判定表

| 请求 | 结果 | 原因与处理 |
| --- | --- | --- |
| 走路 + 右手挥手 | 支持 | 基础层继续步态，右臂覆盖；躯干装饰服从步态与稳定性 |
| 坐着 + 挥手 + 说话 | 支持，需已有坐姿 | base 保持坐姿，手臂与嘴分离 |
| 左手拿杯 + 右手指向 | 支持，需有效握持点 | 左手保留资源，右臂独立执行 |
| 右手拿杯 + 右手挥手 | 冲突 | 若请求允许 auto 可换空闲手；明确指定 right 时排队或拒绝 |
| 看用户 + 点头 | 条件支持 | 单一 head controller 合成；若都争用同一旋转属性，降低装饰或轮流执行 |
| 眨眼 + 嘴型 + 头部视线 | 通常支持 | 必须确认不同 Slot / 属性，不覆盖同一张整脸 Attachment |
| 爬行 + 双手挥手 | 不支持同时执行 | 双手是支撑资源；先转换到允许释放手的姿态 |
| 跑步 + 坐下 | 顺序执行 | 停止移动、对齐座位，再进入落座转换 |
| 持物 + 强烈身体蹦跳 | 条件支持或降级 | 需要检查握持和身体运动；不能只因骨骼写集不同就放行 |
| 躺着 + 站姿招手 | 不能直接混合 | 使用躺姿专用变体，或先起身 |

### 8.6 抢占、取消与降级

约束和资源占用是可行性条件，不能简单被高优先级覆盖。对于可行请求，顺序为：用户明确操作 → 当前对话表达 → 自主行为 → 待机装饰。相同级别按确定性规则处理，默认较新的明确请求可在允许的退出阶段抢占。

每项动作声明能否中断、最迟退出窗口、是否需要恢复以及失败策略。新请求只取消与其冲突的通道，不清空所有轨道。取消右手挥手时，走路、左手持物和嘴型应继续。

降级只可移除 optionalChannels 或使用预先批准的替代动作。`hand:auto` 可以换手；明确指定的手侧不得悄悄更改。队列有数量和生存时间上限，过期意图返回 `expired`，避免几秒前的手势突然补播。

### 8.7 组合 Recipe 示例

以下参数依赖相应动作已获批准。两个分支通过同一逻辑时钟启动；`move_to` 的占用包括基础移动通道，挥手分支只能取得不冲突的右臂。

```json
{
  "id": "approach_and_greet",
  "steps": [
    {
      "parallel": [
        {
          "action": "move_to",
          "params": {"target": "anchor.user_near"}
        },
        {
          "action": "wave",
          "params": {
            "hand": "right",
            "preset": "wave.small.happy.v1"
          }
        }
      ],
      "join": "all",
      "onFailure": "cancelGroup"
    },
    {
      "action": "look_at",
      "params": {"target": "viewer", "holdSec": 1.5}
    }
  ]
}
```

`parallel` 必须定义 join 和失败策略。`cancelGroup` 取消同组尚未完成的实例，并执行必要的安全恢复；不能回滚已经发生的世界位移。需要“移动失败但仍挥手”时，应明确使用独立失败策略，不能依赖隐含行为。

### 8.8 每帧执行顺序

1. 推进一次逻辑时钟，处理新意图、取消与阶段边界，得到通道执行计划。
2. 更新演员世界位置和整体朝向，解析固定接触目标到各视图的局部空间。
3. 对每个视图执行该版本的 AnimationState update / apply，得到基础与覆盖层姿态。
4. 应用经过仲裁的小幅局部偏移、面部状态和约束目标；每种属性由一个受控出口写入。
5. 按匹配版本的顺序计算世界骨骼变换与约束，得到最终姿态；额外修正若需重新求解，必须有明确的有限更新流程，不能重复累计偏移或重复推进物理时间。
6. 从最终手部锚点更新随身物件；检查接触误差并发出一次性逻辑事件。
7. 绘制需要显示的 Spine 视图，更新纹理，最后渲染 Three.js 场景。

同一帧里只推进一次行为语义时间。前后视图各自计算骨骼，但共享实例阶段、选择结果和事件账本。

## 9. 混合、时间与姿态状态机

### 9.1 单一逻辑时钟

场景、动作与前后视图共享单调递增的逻辑时间。每个动作实例保存起始时间、相位、参数快照和随机种子。随机眨眼可以不同，但同一录制的回放必须使用相同种子。

窗口暂停或系统休眠后恢复时，不能把长时间间隔一次施加给动作和角色位移。暂停策略应明确：冻结场景逻辑，恢复后继续；语音若已停止则取消相应嘴型。不要把积压的全部动作事件在一帧内补发。

### 9.2 阶段模型

动作允许以下阶段：`prepare → stroke → hold/loop → recover`。并非每项动作都包含所有阶段。关键事件使用语义标记，例如 `grip`、`footPlant`、`seatContact`、`release`。

等待某阶段结束必须有确定的终止条件。持续视线和持物状态与一次性动作分离，不能让一个永不结束的动作堵塞所有后续 Recipe。

事件记录使用动作实例 ID、逻辑时间和 marker。前后视图共用一份语义事件；Spine 内部与显示有关的事件可以保留，但交互副作用必须经调度器去重。

### 9.3 进入与退出

使用 Spine `AnimationState` 的轨道替换与混合实现姿态接续。切换应从正在播放的状态进入新动作，不先恢复参考姿态。取消后使用对应版本的空动画混合或明确恢复动画，把局部所有权交还基础层；单纯清除轨道可能留下最后姿态，需要按官方行为实现。[Applying animations](https://esotericsoftware.com/spine-applying-animations)

起始混合时长可使用：微表情 0.05–0.12 秒，普通手势 0.12–0.25 秒，全身变化由专用转换决定。这些是测试起点，不是所有动作的统一常量。

普通混合不保证速度连续、支撑稳定或姿态合理。出现具体的速度跳变后，可以增加匹配参考姿态、过渡曲线或有限惯性平滑；第一阶段不先造通用 Inertialization 系统。

### 9.4 姿态图

首版状态图只建设已验证的边：standing ↔ seated、standing ↔ crouched；之后按素材能力增加 crouched ↔ prone、prone ↔ supine 等。进入状态必须存在落地的转换动作、合法支撑和完成条件。

没有必要为每对姿态制作直接转换。请求从躺姿走路，可以经已批准的起身路径到 standing，再开始步态。路径不存在时返回 `unsupportedTransition`，不能把两张姿态直接长时间混合后宣称完成起身。

`crawl` 是需要支撑手脚的移动行为，不只是 `prone` 加世界平移；它应有自己的接触阶段和能力门槛。

### 9.5 步态与世界移动

行走动作先复用资源中已有、可验证的步态，并标定原生步频与视觉步幅。Scene Controller 决定世界速度，步态控制器据此调整相位速度，在批准的变速范围内匹配移动。

超出范围时切换 walk / run，或降低世界速度；不能无限加速一段行走曲线。转身、启动和刹车是需要检查的独立过程。支撑脚漂移应通过相位与速度校准、有效 IK 或受限姿态修正处理，而不是任意修改脚部贴图位置。

## 10. 场景交互、表情与语音

### 10.1 场景锚点

每个交互对象声明 `approach`、`contact`、`facing` 和所需姿态。椅子可以包含脚前站位、臀部落座点和朝向；杯子包含握持点与可放置点。锚点具有世界位置和方向，角色适配器负责映射到纸片局部可达空间。

执行坐下的顺序是：检查座位能力和占用 → 接近站位 → 刹停并对齐 → 播放专用落座动作 → 在 `seatContact` 建立支撑状态 → 保持坐姿。站起按相应转换释放支撑。

物件处于纸片平面之外且不可达时，应调整角色位置或拒绝交互。不能在二维手臂不动的情况下把物件瞬移到三维空间中，伪装成自然伸手。

### 10.2 首版交互清单

先实现看向用户、到达地面目标点、挥手回应、坐到固定椅子、触碰固定桌边，以及一只手持有一个物件。后两项依赖实际骨架和美术能力；可以晚于对话与手势上线。

每项交互都要有开始条件、成功事件、取消路径和结束姿态。避免只有一个 action 名称，却没有物件位置、手部占用或失败处理。

### 10.3 面部能力分级

| 资产能力 | 支持方式 |
| --- | --- |
| 独立嘴部 Attachment | 将 viseme / 开合状态映射到已存在附件 |
| 可变形嘴部 Mesh 或骨骼 | 在明确绑定和范围内驱动 |
| 只有整脸表情 Attachment | 使用离散表情；眨眼和嘴型可能互斥，需合成美术或降级 |
| 没有可用嘴部变化 | 保持原脸，使用说话状态和气泡；不宣称完成口型同步 |

眨眼、眉毛、注视和嘴型都通过同一属性系统声明控制范围。呼吸和头发轻摆优先复用原资源；程序化 secondary motion 只补充缺失部分，避免双重摇摆。

### 10.4 LiveTalker / TTS 接入契约

LiveTalker 是后续适配器，不作为第一阶段环境前置。接入时检查现有服务实际输出，映射为内部 `utterance_id`、播放开始、播放进度、viseme 或能量、结束与取消事件。本 Spec 不假定它已经提供某个特定 API。

以实际音频播放时钟驱动嘴型，而非 LLM 文本生成时间。若只有音量信号，可做粗粒度开合并明确质量等级；若有音素时间戳，再建立更细映射。取消一段语音时同时失效旧的嘴型事件，防止后续对话仍受旧音频控制。

身体手势通过少量语义 cue 对齐语句或强调点，不要求每个字触发动作。视线保持、眨眼和嘴型可并行，但不会因此获得真实资产中不存在的独立面部自由度。

## 11. 对话与运行时协议

### 11.1 MotionIntent

运行时只接受已注册动作与允许参数。LLM 接收精简能力表、当前姿态、手部占用、目标对象和可用预置；不接收整个骨架的每帧状态，也不负责更新物理位置。

```json
{
  "schemaVersion": 1,
  "requestId": "turn-12-motion-1",
  "action": "wave",
  "params": {
    "hand": "auto",
    "preset": "wave.small.happy.v1",
    "amplitude": 0.8,
    "cycles": 2
  },
  "source": "dialogue",
  "expiresInMs": 1500
}
```

`preset` 是动作目录允许的公共引用字段，其余参数按对应 action 校验。`source`、优先级和请求 ID 最终由可信适配器确认，模型不能把自己伪装成系统约束控制器。

回复文本与 MotionIntent 可以独立流出。文本失败不应锁住角色，动作失败也不应阻止正常回复。第一版不要求同一个巨型 JSON 同时包含完整文本、语音和数百个关键帧。

### 11.2 响应和错误

动作提交先返回 `accepted`、`queued`、`rejected` 或 `expired`，随后通过实例事件报告 started、marker、completed、cancelled、failed。相同 requestId 重复提交必须幂等，不能重复挥手或重复抓取。

拒绝原因包括：未知动作、未知参数、范围错误、角色能力不足、视图不支持、姿态路径缺失、资源冲突、目标不可达和版本不匹配。错误附带允许的替代项，便于上层修正；不自动执行任意 LLM 生成代码来补齐能力。

### 11.3 运行时生成新曲线的地位

P0–P3 不把未审阅的长 Timeline 接入普通对话播放。Motion Lab 允许 LLM 生成并即时预览候选，用于真实质量实验。未来可以增加受控“即时创作”开关，但它需要独立的延迟、失败恢复和质量数据。

运行时对已批准动作做有界调参是正式路径；新曲线是否能免审阅实时上线，由实验结果决定，不能把离线成功直接等同于运行时可靠。

## 12. 实验室界面与开发体验

实验室必须让开发者能看清“模型生成了什么”和“运行时实际执行了什么”。主区域显示角色，辅助区域显示动作与参数、通道占用、当前阶段和诊断。调试信息仅出现在 Lab，产品房间不显示骨骼名、轨道号或 JSON。

| 功能 | 必须提供的能力 |
| --- | --- |
| 资源检查 | 正反面、原动画、骨骼与 Slot 查看，缺失资产诊断 |
| 候选对照 | 原始输出、修订版和参考并排或同镜头切换 |
| 参数编辑 | 按动作分类的有效参数；显示单位、范围和来源 |
| 时间控制 | 播放、暂停、逐帧、循环区间、速度显示 |
| 组合检查 | 各通道拥有者、实际属性写集、冲突与降级原因 |
| 录像 | 固定种子与镜头，一键执行标准用例并保存录像和日志 |
| 导入与导出 | JSON 候选、批准预置、RigProfile 和实验记录 |

不需要第一阶段做可视化节点编辑器。Recipe 用小型 JSON 即可，等真实组合需求稳定后再考虑图形编辑。

### 13.2 关键接口

```typescript
interface MotionRuntime {
  submit(intent: MotionIntent): SubmitResult;
  cancel(instanceId: string, reason: string): void;
  tick(dtSec: number, context: RuntimeContext): void;
  snapshot(): MotionSnapshot;
}

interface CharacterView {
  applyPose(frame: PoseFrame): void;
  render(): void;
  getAnchor(role: string): LocalAnchor | null;

}
```

这些接口表达边界，具体类型需在实现时按本 Spec 的字段落地。`CompiledMotion` 需携带属性写集、约束依赖、阶段与视图 ID，不能只返回一个匿名 Spine Animation。

### 13.3 版本与持久化

所有可持久化结构带 schemaVersion。角色绑定变化后，依赖旧绑定的 Draft 与 Preset 必须重新验证；不能静默套用到同名新骨架。动作哈希覆盖曲线、绑定版本、参数定义和风格映射。

角色清单记录前后视图、资产相对路径、导出版本、标定尺寸、默认动画、能力与各动作实现。一个逻辑 Preset 可以有两个 `viewImplementations`，分别引用正面和背面曲线，统一阶段语义和总时长。

原始资产、项目代码和新编写的配置分别记录来源。Spine Runtimes 有专门许可条款，不能按普通 MIT 依赖处理；分发时按官方条款和资产授权组织文件。用户提供的游戏资源默认保存在本地，不自动打包进公开仓库。[Spine Runtimes License](https://esotericsoftware.com/spine-runtimes-license)

## 14. 分阶段实施与交付门槛

### P0：真实资产与基线播放器

完成资产版本检查、同版本格式导入、官方运行时接入、原动作播放和 RigProfile 初始绑定；同时核实正反面能力。此阶段使用 Lab，不建设完整房间或对话。

交付 `asset-report.md`、角色清单、绑定文件及原动作与骨骼探针录像。通过条件是实际拉菲在官方运行时中正确播放，能证明部位与控制方向。背面尚不可用时明确标记，并允许进入单视图 P1；完整转身仍需后续补齐背面验收。已有原始文件，不应重复索要相同资产。

### P1：LLM 动作参数实验

实现 MotionDraft Schema、Compiler、预览、候选记录和参数导入。对第 2 节六项动作执行一次生成及最多三轮反馈实验，保留失败样本。完成可读的原始与修订对照录像。

按附录 D 的真实骨骼结构完成字段生效与参数影响探针。记录本次创作究竟修改了参数、曲线，还是 Primitive 函数；只有固定函数和绑定之后的尝试，才进入“LLM 仅调参”统计。

通过条件：至少建立一条从真实骨架上下文到新数值曲线再到渲染的完整链路，并得到足以判断质量的六项实验记录。只有达到第 15 节动作质量门槛的候选进入正式 Preset 库。

这一阶段的研究可以得出“效果不足”。若多轮后仍无法稳定产出可用动作，保留播放器与数据结构，改为复用优质原动画、由 Agent 辅助小范围调节和少量专用制作；不自动恢复 ARDY，也不继续扩大未经验证的参数空间。

### P2：参数库、并行与中断

实现 Parameter Registry、属性写集、固定轨道、资源占用、Recipe 和取消逻辑。优先用已验证步态加新手势测试“走路 + 挥手”，再测试“左手持物 + 右手指向”。缺少持物能力时先记录该能力未通过，不用漂浮物件冒充。

交付并发、冲突、局部取消、换手和随机相位中断录像与日志。动作必须能混入正在进行的基础动作，并能交还控制权；不能要求每次等整段动画播完。

### P3：有限房间与简单交互

建立房间、有限镜头、路点、固定椅子和物件锚点。增加少量必要的姿态转换。优先完成 standing ↔ seated；蹲、趴、躺和爬按资产能力逐项加入，不同时立项全部动作。

交付到达目标、刹停、落座、起身及一项接触交互的连续录像。通过条件是位置、姿态和接触逻辑一致，中途取消不会留下错误占用或悬空状态。

### P4：对话、语音与桌面常驻

接入 MotionIntent 选择和有界调参、现有 TTS / LiveTalker 适配、取消与播放时钟，再用 Electron 承载同一渲染器。密钥保留在宿主或受控本地服务，不写入前端资源。

Electron 采用维护中的稳定版本，关闭 nodeIntegration，启用 contextIsolation 与 sandbox，通过有限、验证过的 IPC 暴露所需能力；不把 LLM 输出直接连接到文件系统或系统命令。[Electron Security](https://www.electronjs.org/docs/latest/tutorial/security)

交付可启动的 Windows 原型，以及对话期间行动、视线和嘴型的同步与中断演示。桌面透明、置顶和多显示器行为按实际系统验证，Windows 壁纸层集成单独排期。

### 阶段依赖

P0 决定资产是否可用；P1 决定 LLM 创作质量；P2 决定组合架构是否成立；P3 决定场景交互边界；P4 决定产品整合体验。可以提前搭建接口占位，但不能用后续功能完成度替代前置证据。

阶段完成是工程验收条件，不是要求每一步暂停等待用户授权。开发 Agent 应继续执行已授权范围内的可逆工作，记录判断并提供可审阅产物；遇到真实缺失的资产或服务时，完成其他可推进部分后说明阻塞项。

## 15. 质量、性能与录像验收

### 15.1 动作质量量表

对每项候选以 0–5 分评价四项：部位协调、节奏与重量感、轮廓可读性、与角色风格的一致性。初始进入 Preset 库的门槛为平均至少 4 分，单项不少于 3 分，且无以下硬失败。评分是审阅结果，不是从 JSON 合法性计算出的质量保证。

硬失败包括：缺失部件、明显穿身或反关节、切换时弹回参考姿态、错误正反面、物件重复生成、持物无故释放、承诺保持接触却明显脱离，以及取消后无法回到可执行状态。

第一版允许 Agent 做初审并记录理由，提供用户可直接观看的录像；不把“尚无人观看”标记成最终主观质量已获用户认可。首轮实验同时报告一次生成合格率、修订后合格率、迭代次数和人工修改量，不只展示最佳样本。

### 15.2 关键用例

| 编号 | 用例 | 必须观察的结果 |
| --- | --- | --- |
| A01 | 原动画、正面与背面 | 与资源基线一致，贴图和轮廓正确 |
| A02 | 六项 LLM 候选原版与修订版 | 参数可追溯，实际差异可见，无人为替换冒充生成 |
| A03 | 同一手势在 20%、50%、80% 相位被替换 | 从当前姿态混合，不弹回站姿，不等待整段完成 |
| A04 | 走路中挥手，再只取消挥手 | 步态与世界位移持续，右臂平滑交还基础层 |
| A05 | 左手持杯，右手指向，角色轻微转身 | 左手占用保持，物件跟随正确，事件只触发一次 |
| A06 | 对占用中的右手请求挥手 | auto 可用左手；明确 right 时返回排队或冲突 |
| A07 | 坐姿看用户并说话、眨眼 | 合法属性并行；整脸附件限制被正确处理 |
| A08 | 跑向椅子后坐下 | 先减速对齐再落座，不能直接混合成滑行坐姿 |

| A10 | 暂停、恢复、重复请求、语音取消 | 没有大步跳时、重复动作和旧嘴型滞留 |
| A11 | 单参数变化与头部控制探针 | 参数变化实际到达所声明的骨骼、锚点或可视结果 |

接触类用例可以记录锚点误差，初始目标为稳定接触段误差不超过约 0.02H；需要排除接触开始和释放阶段，并根据实际图像调整阈值。未实现 IK 的角色不得以此声称具备固定世界接触能力。

### 15.3 必须交付的录像

`01_asset_baseline.mp4`：原动作、正反面及主要骨骼探针。`02_llm_candidates.mp4`：六项候选的原始与修订对照，每项至少两个完整周期或两次执行。

`03_blend_interrupt.mp4`：相同素材的硬切与官方混合对照，以及随机相位中断。`04_parallel_actions.mp4`：并行动作、占用冲突和局部取消。`05_room_interactions.mp4`：目标移动、落座、接触与转身；随 P3 完成交付。

画面显示动作 ID、版本、逻辑时间和简短状态；详细参数与事件另存 JSON。纸片角度检查至少覆盖正面、斜面、接近侧面、越过侧面和背面，例如 yaw 为 0°、45°、89°、91°、135°、180°。

使用真实渲染录屏，不加速、不补帧、不用生成式视频修复动作。浏览器自动化或离线逐帧导出可以用于确定性对照，但不能作为实时帧率证据；实时性能录像应在目标机器上单独测量。

### 15.4 性能目标与测量边界

以 RTX 4060 8GB 所在的实际用户机器、1080p 窗口、一个角色和简单房间为首个参考场景，同时记录 CPU、系统、浏览器或 Electron 版本、纹理尺寸和 Spine 版本。

| 指标 | 初始目标 | 测量范围 |
| --- | --- | --- |
| 画面刷新 | 以稳定 60 FPS 为目标；p95 帧间隔不高于约 20 ms | 预热后连续场景，报告卡顿分布 |
| 参数与调度 CPU | 每帧合计 p95 约 1 ms 内 | 不含 Spine 网格更新、GPU 上传与场景渲染；分别列出后者 |
| 意图就绪到可见响应 | p95 不高于约 50 ms | 从通过校验且可立即执行算起；排队单独计时 |
| LLM 延迟 | 实测 TTFT、完整 Draft / Intent 时间 | 不与本地动画响应混为一谈 |
| 内存与 GPU 成本 | 记录峰值、稳定值及纹理开销 | 不宣称动画系统零显存；GPU 测量能力不足时明确说明 |
| 持续运行 | 至少 30 分钟循环与交互 | 检查纹理、动画实例、监听器和物件是否持续增长 |

这些数字是预算，不是本 Spec 已测出的结果。云端无 GPU 或软件渲染环境只能验证功能，不能替代目标机器性能验收。出现瓶颈先定位画布纹理更新、Spine 几何更新、透明过绘或桌面宿主开销，再决定优化。

### 15.5 需要的自动化检查

自动测试集中覆盖 Schema 与范围拒绝、属性写集过滤、并发仲裁、局部取消、请求幂等、前后视图事件去重、时间暂停恢复和接触占用释放。这些规则容易造成真实运行错误，值得测试。

针对字段被忽略和约束覆盖的风险，补充参数有效性探针与版本适配采样测试。对一条 0° → −72° → 0° 的线性示例，检查关键时刻的真实局部旋转；对归一化 Bézier，检查中间采样值。再验证腿部参数确实通过 IK 目标生效，没有被仍启用的 IK 覆盖。

动作是否可爱、是否有重量感，必须通过可视结果判断；不写“输入 wave 就返回 wave”的测试替代动画验收。

## 16. 风险与可调整的决策

| 风险 | 早期证据 | 应对方式 |
| --- | --- | --- |
| 实际资产版本老旧 | P0 加载报告 | 锁定匹配运行时；不强行迁移全部素材 |
| 正反面拓扑不同 | 双视图探针 | 视图专用绑定和实现，共享语义阶段 |
| LLM 曲线合法但不好看 | P1 对照与评分 | 控制参数空间、增加可视反馈、保留少量优质原动画与专用制作 |
| 参数组合数量膨胀 | P2 冲突日志 | 限定动作族与已验证范围，使用必需/可选通道，不枚举所有情绪组合 |
| 父骨骼影响持物与脚 | 接触误差 | 加入依赖与接触约束，限制躯干装饰 |
| 纸片纹理限制遮挡 | P3 真实交互 | 首版限制交互位置；明确需求后评估分层或直接 Mesh 渲染 |
| 站立素材不足以躺爬 | 姿态预览 | 补专用动作或 Attachment；明确能力缺失 |
| 过早产品化掩盖动作问题 | 缺少 P1 / P2 录像 | 先交付实验结果，再扩展房间和桌面 |

与 ARDY 相比，这一路线把主要成本从模型部署和成人骨架重定向转移到动作创作、角色适配与组合规则。它更适合本项目明确选择的有限 Q 版表现，但不具备任意人体动作的生成上限。维护成本低的前提是约束动作目录和视图数量，而不是宣称所有行为都能被几个参数自动覆盖。

未来最值得投入的是：LLM 结合真实渲染反馈的动作修订、少量动作族的参数优化、接触感知组合、语音节奏与手势同步，以及跨少数角色的绑定复用。重新引入生成式 Motion Model 应由明确的新需求触发，例如开放式复杂全身动作，而非因为动作库需要增加几个预置。

## 17. 首次开发执行清单

1. 初始化 TypeScript / Vite 项目，创建 Motion Lab 入口和最小数据类型。
2. 导入一名实际角色，检查 Spine 版本；锁定官方运行时与依赖。
3. 播放原动作，确认正反面、透明度、脚底标定和截图一致性。
4. 生成 AssetReport，完成首批语义骨骼探针与 RigProfile。
5. 实现 MotionDraft 校验和匹配版本的 Timeline 编译，保存原始候选。
6. 让 LLM 创作六项动作，记录原始结果、修订和录像，做出质量判断。
7. 批准可用 Preset，建设参数分类、实际属性写集和局部混合。
8. 验证走路 + 挥手、持物 + 指向、冲突与取消，再进入有限房间。

在第 6 步获得证据之前，不下载人体动作模型，不批量收集动作数据，不建设完整桌面聊天产品，也不制作庞大的参数后台。

## 附录 A：数据契约最低要求

### A.1 MotionDraft / 曲线

| 字段 | 必须满足 |
| --- | --- |
| schemaVersion、id、rigProfile | 已知版本；ID 唯一；绑定版本明确 |
| durationSec | 有限正数；受动作创作预算限制 |
| channels | 已注册语义通道；与编译后的写集一致 |
| phases | 秒；非递减且位于 [0, durationSec]；必要阶段必须有非零长度 |
| curves | 每条指定 role、property、mode、keys；不能重复写同一属性 |
| keys | 时间严格递增，数值有限；需要的开始与结束姿态明确 |
| ease | linear、stepped 或有界 Bézier；属于当前关键帧到下一帧的区间 |
| requirements | 合法姿态、能力、视图和资源；不存在的要求不能被忽略 |
| provenance、approval | 来源和候选历史；draft 不能冒充 approved |

rotate 值为角度；translate 值为 `[xH, yH]`；scale 值为 `[sx, sy]`；Attachment 值是允许集合中的名称。不同 property 使用判别联合 Schema，不能把任意类型塞入 value。Attachment 只允许 stepped 切换。

循环段首尾需要姿态连续；速度是否连续另外检查。不能仅因首尾角度相同就判定循环平滑。缺失的恢复段不能由 Compiler 随意猜测成自然动作。

### A.2 ParameterDefinition

必须包含名称、类型、单位、默认值、有效域、已验证域、允许动作、影响属性、映射语义与 updatePolicy。继承关系不得成环；未知键拒绝；动作快照保留最终值与每个值的来源。

同时声明 affectedProperties、observableRoles、activePhases，以及参数有效性检查记录；具体要求见第 7.8 节。

StyleProfile 只引用注册参数与明确映射。骨骼绑定、安全范围、RuntimeContext 和资源所有者不能被 StyleProfile 覆盖。

### A.3 MotionInstance / Scheduler

实例至少包含 instanceId、requestId、presetVersion、viewImplementations、参数快照、阶段、逻辑时间、状态、writes、dependsOn、resources、contacts、优先级、到期时间与取消策略。

调度顺序为：验证请求 → 解析动作与参数 → 检查能力与姿态路径 → 计算属性及资源需求 → 仲裁 → 创建实例 → 驱动阶段 → 发送一次性事件 → 释放或转交资源。

属性平滑权重不能改变语义所有权。例如旧挥手在混出时仍影响右臂数值，新动作已经成为该通道的主要拥有者；它们是一次受控过渡，不是两个互不知情的动作同时写入。

### A.4 Recipe

允许有限的 sequence、parallel、动作引用、阶段或事件等待，不支持脚本执行、任意递归和无上限循环。第一版嵌套深度建议最多两层，步骤数和等待时间设置上限。

parallel 声明 join = all 或 first，并明确失败策略。first 成功后对其余分支执行定义好的取消与恢复，不留下后台动作。被取消的等待不能在未来收到旧事件时再次恢复。

## 附录 B：给首个开发 Agent 的启动指令

请按本 Spec 新建 Pliette，先完成 P0 与 P1，再推进参数组合。使用实际 Spine 资产和匹配版本的官方运行时；保留资源骨架、Mesh、Slot 和动画能力。没有实际资产时，先完成导入与官方样例验证，明确剩余验证项。

原始拉菲 lafei_8 已确认是 Spine 3.6.52，结构事实见附录 D。先解决同版本文件导入，再正确播放原动作。用户已放弃参考另一会话的自制渲染实验，不继承该播放器，不等待其产物，不重新实现蒙皮、约束与绘制顺序。将参数、组合与交互逻辑建立在官方运行时之上。

优先验证 LLM 生成数值动作参数的质量。你可以作为 Author 提出 MotionDraft，但必须保留第一次输出、每轮修订、参数文件与真实渲染录像。不能把选择原有动画当作新动作生成，也不能只交付合法 JSON 而不观察画面。

参数模块以真实骨骼属性写集、通道占用和接触依赖为核心。实现走路时挥手、左右手独立动作以及局部取消；说明冲突、降级与恢复结果。复用 Spine 官方混合，避免重写播放器。

不要引入 ARDY、真人动作提炼、3D→2D 重定向、通用自动骨架或庞大插件架构。先提交可运行的 Lab、可追溯的实验和录像，再扩展房间、语音与桌面宿主。完成已授权的可逆工作，不为每个常规实现选择反复请求确认。

### D.3 首个 RigProfile 的绑定候选

以下名称和父子关系已从二进制读取；语义用途是待可视探针确认的候选，不能只靠名字直接批准幅度。

| 候选用途 | 实际节点或关系 | 控制注意事项 |
| --- | --- | --- |
| 演员内部整体 | root → bone | 场景世界移动放在外层 Actor；内部节点用于有限姿态表达 |
| 躯干 | bone → body | body 的 setup rotation 约为 −90°；使用偏移，避免当作直立 0° |
| 头部 | bone → face | face 与 body 是兄弟节点，不能假设躯干旋转会自动带动头部 |
| 左臂 | body → hand_L → hand_L3 | 是两级候选控制链；可视确认后开放上下段参数 |
| 右臂 | body → hand_R → hand_R3 | 与左臂独立写属性，但共享 body 祖先 |
| 左腿 IK | leg_L1 → leg_L3；目标 leg_L | 目标挂在 root；不是名为 leg_L 的大腿旋转骨 |
| 右腿 IK | leg_R1 → leg_R3；目标 leg_R | 与左腿各自求解，仍需共同协调支撑和身体移动 |
| 眼睛 | face → eye_L / eye_R | 可结合实际附件做状态切换，不假定具备任意视线角度 |
| 嘴部 | 尚未确认独立控制能力 | 不从名称清单推定已有完整口型；缺失时单独补附件能力 |

因此，“一边走一边挥手”首先可拆成腿部目标轨迹和右臂局部曲线；身体起伏与倾斜作为有预算的协调项。“看用户同时点头”可能争用同一个 face 局部旋转，应由头部控制器合成目标，而不是各开一个轨道互相覆盖。

### D.4 官方播放路径与文件转换

首版明确采用：同版本 JSON 数据 → 官方 spine-ts 3.6 SkeletonJson → 官方 Skeleton / AnimationState / WebGL 渲染 → 完整角色画布 → Three.js 纸片表面。3.6 Web Core 源码包含 JSON 读取和动画求解；不能把其他版本的 SkeletonBinary API 名称复制进来便认为可读当前二进制。[Spine 3.6 官方 Web Core](https://github.com/EsotericSoftware/spine-runtimes/blob/3.6/spine-ts/build/spine-core.js)

现有 skel 优先通过兼容版本的官方 Spine 工具进行一次性导入，再导出 3.6 JSON。保留原文件，记录工具版本和转换产物哈希；不修改版本字符串冒充升级，不重建网格，不重新绑骨。原始 Nonessential 为 false，转换流程应保留运行语义，不把缺少编辑元数据当作必须重做资产的理由。[Spine 数据导入](https://en.esotericsoftware.com/spine-import)

若没有可用转换工具，按第 3 节记录具体导入缺口。仅在确有需要时实施独立离线格式转换器，参考官方对应版本读取实现，并验证骨骼、权重、约束、动画采样与绘制结果。转换工具不得承担新的蒙皮算法或渲染工作。

### D.5 参数编译与验收顺序

当前 3.6 SkeletonJson 的旋转关键帧读取 angle；内部 MotionDraft 的 value 必须显式映射。3.6 曲线通过 CurveTimeline.setCurve 接收归一化控制点，不能直接套用 4.x 的字段与控制点规则。优先构造版本匹配的 Timeline 对象，使用该版本 API 的实际采样结果验收。[Spine 3.6 官方 Web Core](https://github.com/EsotericSoftware/spine-runtimes/blob/3.6/spine-ts/build/spine-core.js)

1. 在官方运行时正确播放原有动画，确认原画、图层、网格和透明度。
2. 对 face、左右手链和腿部 IK 目标逐项做小幅探针，建立能力与有效范围。
3. 固定一个小挥手 Primitive，由 LLM 只生成有界数值参数，保留首次输出和修订录像。
4. 增加步态控制，再验证走路与挥手并行、局部取消和控制权交还。
5. 最后加入完整正反面、3D 房间、物件接触及语音同步。

当前资产信息足以把参数与绑定设计写具体；它本身不证明新动作自然、背面完整或实时性能达标。这些结论由后续官方运行时中的可复现结果给出。
