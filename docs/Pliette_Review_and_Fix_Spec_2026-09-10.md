# Pliette 实现验收与下一轮修复任务

审查日期：2026-09-10。面向 Eddy 与接手修复的 zcode / 开发 Agent。

审查仓库：[ApolloEddy/Pliette](https://github.com/ApolloEddy/Pliette)。固定提交：[5c1461d5e62ec04e988bf484761f1987f1f0e909](https://github.com/ApolloEddy/Pliette/commit/5c1461d5e62ec04e988bf484761f1987f1f0e909)。依据为用户工作报告、仓库中的 Motion Guide Spec、实现代码与已保存实验记录。

## 1. 验收结论

**已有实质工程成果，可以作为下一轮迭代基线；尚不能按“Spec 全部完成”验收。**

控制档案、协议、校验模块、官方运行时编译、实验脚手架和第二模型档案已经建立。工作报告也明确承认视觉评分未完成、在线门槛未达标，这一点应保留。

目前的阻塞不只有生成延迟：运行时指导片段混入错误角色知识，请求替换存在确定性缺陷，轨迹采样漏检，Lab 播放未接入所要求的分层交权，实验口径还不足以判断指导书收益。现有结果既不能证明“指导书无效”，也不能证明“换更快模型即可达标”。

下一轮顺序：**修正知识装配与运行时正确性 → 修正实验记录和统计 → 完成视觉与中断验收 → 再比较延迟优化方案。**

## 3. 必须修复的问题

### F1 · P1：不同模型收到同一段拉菲专属指导

证据：[context.ts：buildGuideExcerpts](https://github.com/ApolloEddy/Pliette/blob/5c1461d5e62ec04e988bf484761f1987f1f0e909/src/motion/author/context.ts#L56)，[spineboy 档案](https://github.com/ApolloEddy/Pliette/blob/5c1461d5e62ec04e988bf484761f1987f1f0e909/characters/spineboy.rig-profile.json)。**已复现。**

`buildGuideExcerpts(profile)` 无条件追加“头与躯干是兄弟节点”“眼睛只能通过 face.eyes.pair 切换”和 `torso.bob` 的拉菲反例。spineboy 档案却明确说明头随 hip/躯干联动，而且没有 `face.eyes.pair`。因此实际送给 LLM 的请求内部自相矛盾。独立的 Markdown 指导书正确，也不能抵消请求包中的错误说明。

此外，`controlSubset` 只过滤 `availableControls`，指导片段仍列出整个档案的开放控制，并宣称这些控制“只允许引用”。

**修复要求：**

- 模型拓扑、联动关系、限制与反例都必须来自当前档案及关联证据；通用生成函数不得硬编码某角色结论。
- 结构化源同时生成供人阅读的指导书与实际发送给 LLM 的片段；二者引用相同版本和证据。
- 片段按本次可用控制集合与必要依赖装配。依赖可以用于解释，但不得被列为额外可写权限。
- 案例只能绑定适用的模型、档案版本、视图和控制集合；无证据的说明标记未知。

**验收：** 分别装配拉菲和 spineboy 的真实请求；spineboy 不含拉菲专属兄弟拓扑结论或不存在的眼睛控制。只开放一个控制时，指导书中的可写列表与 `availableControls` 完全一致。测试检查实际请求内容，不能只检查离线文档。

### F2 · P1：新请求漏登记，旧响应还能删除更新请求

证据：[authorBroker.ts：begin](https://github.com/ApolloEddy/Pliette/blob/5c1461d5e62ec04e988bf484761f1987f1f0e909/src/motion/author/authorBroker.ts#L84)，[过时响应清理](https://github.com/ApolloEddy/Pliette/blob/5c1461d5e62ec04e988bf484761f1987f1f0e909/src/motion/author/authorBroker.ts#L131)。**两种情况均已复现。**

复现一：`begin(r1)` 后调用 `begin(r2)`，函数将 r1 标记取消便直接返回成功，未保存 r2；此时 `isStale(r2)` 为真。

复现二：依次 `begin(r1)`、`begin(r2)`、`begin(r3)`，r3 原本有效；迟到的 r1 进入 `commit` 后，过时分支无条件 `active.delete(profileId)`，把 r3 一并删除。

**修复要求：**

- 按既定替换策略取消旧请求后，完整登记新请求；重复请求检查不能顺带取消无关的有效请求。
- 清理必须核对当前记录的 requestId，旧响应不得删除其他请求。
- 以单调时钟记录请求提交时间；生命周期从真正发起生成前开始。
- 生成异常、超时、取消均要按请求身份完成清理。

**验收：** r1→r2 后 r2 可提交、r1 不可提交；r1 迟到时 r3 保持有效；重复 ID、主动取消、超时、状态变化与异常路径有确定性回归测试，且均不产生重复播放。

### F3 · P1：轨迹采样漏掉 Y 轴，且没有覆盖实际播放边界

证据：[sample.ts](https://github.com/ApolloEddy/Pliette/blob/5c1461d5e62ec04e988bf484761f1987f1f0e909/src/motion/author/sample.ts#L112)，[validateV11.ts 的采样调用](https://github.com/ApolloEddy/Pliette/blob/5c1461d5e62ec04e988bf484761f1987f1f0e909/src/motion/author/validateV11.ts#L297)。**Y 轴漏检已复现；其他项来自静态代码核对。**

使用官方 spineboy 骨架，在 hip 上建立 Y 从 0→10→0、持续 1 秒的位移曲线；当前采样返回 Y 最大值 10，却将峰值速率记为 0，且无速率诊断。原因是速率计算只比较 `v[0]`。

相关缺口：位移采样值为骨架原生单位，而控制限速可使用 H/s，未做单位换算；默认跳过最初 0.15 秒的速率评估；采样停在候选 duration，不检查退出过程；现有调用未提供实际基础动画状态，也未模拟真实混合权重。组合控制的子控制筛选还有问题，不能保证子项进入采样。

**修复要求：**

- 每个连续轴都检查速率，并明确按轴还是向量范数限制；数值、范围与单位必须一致。
- 使用档案的标定身高处理 H 单位，缺少必要标定时拒绝开放对应位移控制。
- 正确展开 composite 子控制及其实际写入属性。
- 使用与播放器一致的基础状态、轨道和混合策略，覆盖进入、满权、退出以及交权后的连续性。
- 对最终合成值执行有限性、适用范围和速率检查；仅检查输入关键帧不能替代合成检查。

**验收：** 纯 Y 超速被拒绝；更换骨架尺寸后 H 单位判断保持一致；进入瞬变、退出瞬变、基础动画叠加和组合子项各有针对性测试。任何尚不支持的播放状态必须明确拒绝，不能视为已验证。

### F4 · P1：Author 实际播放仍是轨道 0 整体预览

证据：[playCompiledOnView](https://github.com/ApolloEddy/Pliette/blob/5c1461d5e62ec04e988bf484761f1987f1f0e909/src/lab/ui.ts#L272)，[authorPlayHooks 与状态快照](https://github.com/ApolloEddy/Pliette/blob/5c1461d5e62ec04e988bf484761f1987f1f0e909/src/lab/ui.ts#L716)。**静态代码确认。**

Author 调用了用于孤立预览的函数：瞬间清空 track 0，再把候选作为 track 0 动画播放。日志显示混入/混出时间，但实际调用未使用传入的混合参数。取消也不按实例定位，而是清空 track 0。它尚未实现指定通道上的局部叠加、取消和交还基础层。

`authorStateVersion` 初始化为 1 后没有更新，Author 面板固定解析拉菲档案；快照中的视图和皮肤取自档案，而非核对当前真实状态。播放控制权也未通过该路径登记到既有 scheduler；未看到自然结束时调用 `releasePlayback` 的接线。

**修复要求：**

- Author 候选复用正式 scheduler / gesture layer，按实际属性写集获取和释放控制权。
- 保留基础动画；按实例进行混入、自然退出和局部取消，落实传入的混合参数。
- 从真实模型实例、皮肤、视图、离散状态与占用情况生成快照；对应变化递增版本，使旧结果失效。
- 自然结束和所有异常路径释放播放句柄；不能仅用 FIFO 丢弃记录来替代生命周期回收。
- 将“孤立候选预览”与“在线叠加验收”的入口和结果标识清楚。

**验收：** 基础动画持续播放时分别执行单通道、双通道动作；中途取消只影响该实例；其他轨道继续运行；自然结束恢复正确状态并清理句柄。生成期间换模型/皮肤/离散姿态的旧响应不得播放。提交可观察这些行为的录像与事件日志。

### F5 · P1：实验尚不能量化指导书收益或真实在线成功率

证据：[A/B 请求差异](https://github.com/ApolloEddy/Pliette/blob/5c1461d5e62ec04e988bf484761f1987f1f0e909/scripts/run-abc.mts#L110)，[生成与提交顺序](https://github.com/ApolloEddy/Pliette/blob/5c1461d5e62ec04e988bf484761f1987f1f0e909/scripts/run-abc.mts#L140)。**静态代码与已保存数据核对。**

- A 已包含 `positiveLooksLike`、`negativeLooksLike`、`behavior`、`conditions` 等语义指导；B 主要追加重复控制行与硬编码提示，不能直接代表“最小接口”对“完整指导书”的预期差异。
- A、B 已经经过同一校验与 Broker；C 再复用 B 做一次类似检查。当前三个接纳率不足以拆分首稿质量和程序过滤收益。
- runner 先等待生成及校验完成，再 `broker.begin`，截止计时绕过生成耗时。8 秒配置应用于客户端，但请求装配没有同步覆盖默认 2500ms 预算。
- `play` 回调返回固定的 `sink`，没有真正播放；提交接纳不等于实际执行成功，更不等于视觉通过。
- 成功记录没有逐条完整保存原始输出；部分失败只有截断到 400 字符的片段。配置未完整冻结模型标识、生成参数、实际预算和请求内容，不足以完整复盘。

**修复要求：**

- 明确 A 的最小契约与 B 的新增指导内容，保存完整请求并自动输出 A/B 内容差异；不允许悄悄把 B 的解释全部保留在 A。
- A/B 保存和独立评分原始首稿；C 只作为 B 同一首稿经过程序边界后的执行路径，不产生额外模型调用分母。
- 在发起生成前登记请求，共用同一预算来源；分别记录提交、响应完成、校验完成、实际首帧和播放结束的单调时间。
- 原始响应逐条完整留存，保留解析失败文本；与归一化/清理后的 JSON 区分，不把修复后结果计作原始首稿。
- 冻结模型、参数、提示版本、档案 digest、预算与测试请求集；密钥不得进入实验产物。
- 区分 schema 合法率、motion 接纳率、合理拒绝率、实际执行率、视觉通过率和时延。有效的 `unsupported` 不是成功生成动作。

**验收：** 由独立汇总脚本从逐条记录重建所有指标；每条结果可回溯请求、首稿、诊断及相关录像。A/B 的视觉评分方法和结果完整；C 明确哪些失败被边界拦住，哪些仍然漏过。未产生首帧的请求计失败或超时，不能混入首帧延迟成功样本。

### F6 · P2：Lab 导入候选重建了不匹配的请求身份

证据：[候选导入](https://github.com/ApolloEddy/Pliette/blob/5c1461d5e62ec04e988bf484761f1987f1f0e909/src/lab/ui.ts#L837)，[身份校验](https://github.com/ApolloEddy/Pliette/blob/5c1461d5e62ec04e988bf484761f1987f1f0e909/src/motion/author/validateV11.ts#L81)。**静态代码确认。**

导入时生成新的 `import-*` requestId 和 contextId，却原样校验携带旧身份的候选响应；保存过的在线候选会因身份不符被拒绝。

**修复要求与验收：** 设计显式的离线候选导入流程，保存来源身份和档案版本，重新验证当前上下文并生成新的执行授权。在线响应回显校验继续保持严格，不能为实现导入而全局放松。验收“导出→重新打开→导入预览”闭环，并验证错模型候选仍被拒绝。

## 4. 对现有实验数字的更正

来源：[2500ms 逐条结果](https://github.com/ApolloEddy/Pliette/blob/5c1461d5e62ec04e988bf484761f1987f1f0e909/experiments/motion-guide/run-llm-mimo/results.json)，[8000ms 逐条结果](https://github.com/ApolloEddy/Pliette/blob/5c1461d5e62ec04e988bf484761f1987f1f0e909/experiments/motion-guide/run-llm-mimo-8s/results.json)。

每轮 10 请求 × A/B 各 2 次＝40 次模型调用。C 的 20 条记录复用 B，不是新调用。

| 指标 | 按保存记录重算 |
| --- | --- |
| 2500ms 超时 | 35/40＝87.5%；不是把 C 加入分母后的约 58% |
| 8000ms 超时 | 5/40＝12.5%；不是 5/60 |
| 8000ms A 组 validateOk | 12/20＝60% |
| 8000ms A 组 commitAccepted | 11/20＝55%；其中一个合法响应为 unsupported，未接纳为动作 |
| 8000ms B 组 commitAccepted | 12/20＝60% |
| 8000ms C 组 commitAccepted | 12/20＝60%；复用 B，不是独立模型表现 |
| A 组已接纳记录延迟中位数 | 4349ms，11 条样本 |
| B 组已接纳记录延迟中位数 | 4597ms，12 条样本 |

上述延迟为 runner 保存的生成/校验相关耗时，不能标记为真实首帧延迟。只对已接纳样本统计也不等于全部请求的端到端延迟分布。这批记录没有完成视觉质量验收。

工作报告中的 10 分钟浸泡，对应脚本使用 Mock、占位编译产物与空播放回调。它支持纯逻辑压力测试的结论，不能替代真实渲染、实际网络取消、分层播放和句柄释放的长时验收。[soak-author.mts](https://github.com/ApolloEddy/Pliette/blob/5c1461d5e62ec04e988bf484761f1987f1f0e909/scripts/soak-author.mts)

## 5. 可直接发给开发 Agent 的执行指令

> 以本报告固定提交为审查基线；开始前读取仓库现有 Spec 和实现，并确认后续提交是否已修复对应问题。按 F1/F2 → F3/F4/F6 → F5 的顺序提交可审查修复，保留现有架构和官方 Spine 运行时。每项先建立能失败的针对性回归用例，再修正实现。不得通过删检查、放宽约束、隐式截幅或全局放松响应身份校验来通过验收。已有缺失资产应沿用项目既定本地资产入口；不得伪造视觉证据。先修实验和集成正确性，再进行已获授权范围内的真实模型调用。未获授权的付费调用应交付可运行命令和成本范围，不自行执行。

4. 更正后的历史实验报告；新的实验将完整首稿、派生结果、评分与逐阶段时延分别留存。
5. 清晰列出仍未验收的能力与上线门槛。继续保持在线 Author 默认关闭，直至 Spec 的相应门槛有真实证据支持。

优先级含义：P1 阻塞核心验收，P2 阻塞相应调试工作流；本报告未发现需要按线上生产事故处理的 P0 事项。
